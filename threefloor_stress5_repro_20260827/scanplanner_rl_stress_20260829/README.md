## 三、本批记录到的问题

1. **`boost::wrapexcept<lock_error>` 控制器崩溃 —— 5/5 轮，每次任务结束关停时必现**
   （sim ~529s，任务已完成后 teardown 阶段）。本批无害（成绩已定），但与第一批摔倒路径
   崩溃同签名——**该 bug 在所有退出路径上都存在，不是摔倒特有**。随后伴生
   `Controller Spawner error while taking down controllers: transport error`（5/5）。
2. **spawn 瞬态 `GetModelState: model [a1_gazebo] does not exist`**（每轮 1 次，场景重置瞬间，
   无后续影响）。
3. **预算余量对机器负载敏感**：预算按 wall 计。同 sim 行为下 RTF 0.95→536s（余 64s）、
   RTF 0.89→576s（余 24s）；**若 RTF 跌到 ~0.85，同行为将到 ~597s，贴着 600s 上限**。
   满载机器或与其它 GPU 任务并发时存在超时风险。
4. **跨批次结果翻转（2/5 → 5/5）**：同码同 seed 同场景，第一批 3 轮失稳、本批 0 失稳——
   步态稳定性是策略级随机（policy 推理/控制器时序抖动），**单批 5 轮的通过率不能当作
   可靠性估计**（两批合并 7/10 完成、验收 5/10）。评估需按 n≥10-20 轮计。

## 四、结论

1. 该版本**能力上限已被证明**：5/5 验收满分（18/18 + 全程 + 回厅）在本批全部达成，
   且楼梯全程零守卫触发——上批建议的"楼梯横向保持提前介入"在本批自然未用到。
2. 上批 3 个失稳签名（上行漂移/进门翻倒/下行倾角）本批**一个都没复现**，说明它们是
   低概率尾 event 而非确定性缺陷；合并两批，楼梯相关失稳 3/10、进门 1/10。
3. 待修 bug 优先级不变：①控制器 lock_error（所有退出路径，5/5 必现）②预算余量对 RTF
   的敏感性（部署环境需预留负载评估）。
